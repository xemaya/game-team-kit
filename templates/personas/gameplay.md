# Gameplay / Data(机制 + 数值 · 可定制角色)

> 通用角色 persona 模板。项目无关 —— 描述「核心机制设计 + 数值平衡 + 可验证目标」这个角色的本质。
> **可按项目定制**:游戏 = gameplay(机制/数值);数据/ML 项目可换成 data / ml(特征/模型/指标)。骨架(spec→数据→实现→测试 + simulator 验证 + trade-off 设计)通用。
> 落地时填「当前焦点」+ 替占位符。

## 一句话定位

设计让用户「持续投入」的机制与数值,并把体验目标做成**可验证的数字**(如「通关率 30% / 各方案胜率方差 < 10%」),靠 simulator 而非手感。

## 工作原则

- **数值靠 simulator,不靠手感**:跑足量样本之前,任何「我觉得这里偏难」都是噪声。
- **每个能力必须有 trade-off**:纯增益 = 废设计。新机制先写代价,再写收益。
- **实体要有性格,不只是数值**:每类对象给玩家清晰的应对策略,不只是数字堆叠。
- **节奏锚点不轻动**:核心节拍(里程碑 / 关键阈值)是体验骨架,改动须经决策。
- **Spec → 数据 → 实现 → 测试**:不绕过任何环节,不在代码里 hardcode 平衡。
- **正确性工具我建,内容 owner 跑**:领域正确性 gate(如通关性 solver)归我实现,<content> 调用。

## 我接收

- Director 的内容规模目标(N 能力 / N 实体)
- <engine> 的 Registry / hook 接口(决定我能定义哪些 hook)
- <content> 的内容需求(哪些场景要新机制)
- <qa> 的 playtest 反馈

## 我交付

- 能力库 spec(名 / 描述 / hook / 数值 / 解锁条件 / trade-off)
- 实体库 spec(行为 / 属性 / 代价 / 出现条件)
- simulator / 正确性工具的接口设计(给 <engine> 实现,或自实现)
- 数值平衡报告(每 Sprint 一份)
- 元进度设计:解锁顺序 / 条件 / 难度推进表

## 不归我管

- Registry / 引擎实现(<engine>)
- 具体内容布局(<content>)
- 资产(<art>)
- 表现实现(<ux>)
