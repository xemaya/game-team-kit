# 方法论:AI 多 agent 虚拟工作室

> 本文讲的是「为什么这么设计」,面向**想复用这套打法的人**。
> 如果你只想知道「怎么跑」,看 [`../README.md`](../README.md) 的 quickstart。
> 占位符约定:`<PROJECT>` = 你的项目,`<role>` = 某个工种角色。

核心命题:**这不是「AI 帮我写代码」,是「AI 开了一家工作室,把项目交付出来」。** 区别在于 ——「写代码」是一锤子买卖的代码生成;「开工作室」有分工、有派工闭环、有摁着它别跑偏的约束、有机器守门、有会自迭代的流程、还有翻车了接得住的兜底。下面逐件拆开讲。

---

## 1 / 为什么把 AI 拆成 9 个固定角色

**单个会话的脑子会糊。** 你让同一个 AI 一会儿改内核、一会儿调样式、一会儿写文案,它越往后越乱,前后决策能自己打自己的脸。原因是上下文被不同领域的细节污染,注意力被稀释。

解法:**把工作室拆成固定角色,每个角色就是一个独立会话,各自只在自己一小块地里干活。** 上下文干净,质量才稳。

默认 9 角色(`<role>` 取值):`director` / `engine` / `ux` / `art` / `content` / `gameplay` / `qa` / `release` / `audio`。这套是从一个游戏项目抽出来的,**非游戏项目应当替换**:`art/audio/gameplay` 可换成 `backend/data/ml/devops` 等。判定原则只有一条:**这个项目里有哪几个「能并行、且上下文互不污染」的专业领域?** 一个领域 = 一个角色。

拆角色还带来一个工程红利:**层隔离可以做成硬约束**。例如核心逻辑层禁止 import UI/渲染层(见 §3 HARNESS),违反直接被对应角色拒收。角色边界 = 代码边界 = 测试边界,三者对齐。

---

## 2 / Director 派工闭环

工作室不靠口头沟通,靠文档。**Director(总监)是固定的一个会话:写需求 / 定验收标准 / 派活 / 验收 / 记账 —— 但自己不写代码。** 任何代码改动都派给某个工种 agent。

每个任务的命运:

```
Director 写派工单(handoff doc:Goal / Acceptance Criteria / Coordination 风险 / Not in Scope)
   │
   ▼  claude --agent <role> "<task-id>: 一句话 · handoff 路径"
   │
   ▼  SessionStart hook 自动注入(HARNESS + persona + tasks + 最近 DEC)
   │
   ▼  Agent 执行,每个 milestone 往 Execution Log append 一条
   │
   ▼  Agent 回填 Verification + Handback,status → done,更新自己 tasks.md
   │
   ▼  Director 按验收 SOP 逐条核对 → 过 → 派下一个(循环)
```

派工单的固定模板见 [`../templates/handoff-protocol.md`](../templates/handoff-protocol.md) §2。最关键的两段:

- **Acceptance Criteria** —— 硬性验收点,**尽量写成可机器检查**(grep 模式 / 测试命令 / 数量对账)。这是机器 gate 的入口(见 §4)。
- **Not in Scope** —— 明确划掉不做什么,防止活越干越多(scope creep)。

为什么 Director 不写码?因为「派工的人」和「干活的人」必须分离 —— 否则 Director 自己就成了那个会糊、会跑偏的全能会话。这条边界本身要被约束(见 §3 的 §8 金条款:Director 顺手只能改字面量 / 单条件,超过 3 行 / 跨文件 / 动类型必须派任务)。实践中,即便是 AI 总监也会越权手痒改代码,所以这条铐子是真有用的。

## 3 / 防漂移三件套

AI 最坑的不是不会写代码,是**会跑偏、会忘事、会自作主张改方向**。三样东西摁住它。

### 三件套之一:`HARNESS.md` —— 全局铁律

任何会话第一件事就读它。结构(模板见 [`../templates/HARNESS.md`](../templates/HARNESS.md)):

- **§0 启动前必读** —— 看板 / 最近决策 / 自己的角色与任务。不做就操作 = 违反 harness。
- **§1 不可越线(Hard Rules)** —— 项目无关的硬规矩骨架:
  - 不替用户改 scope(所有 scope 变更经用户,记 DEC)
  - 不跨 agent 私下协作(跨域协调走 Director)
  - 不私自 commit / push / PR(默认 dry 操作,等用户明确请求;hook 失败查根因,不绕过)
  - 不 mutate `decisions.md` 已有条目(append-only)
  - **层隔离**(项目专属,需填:如「核心层禁止 import UI 层」)
  - archive / 只读目录不写新文件
- **§2 必做项** —— task 状态变化更新 tasks.md;方向性判断加 DEC;跨域联动写集成日记;**提交前必须本地验证**。
- **§3 目录契约** —— 哪些目录是 active / gitignored / 只读。
- **§5 锁定的 Scope** —— 项目级决策的速查表(每条挂一个 DEC 号)。

HARNESS 的价值:它把「靠 AI 自觉」的东西变成「写死的红线」。`<PROJECT>` 专属部分(层隔离规则、scope 表、目录契约)在 bootstrap 时填占位符;骨架(§1 五条硬规矩)项目无关,直接复用。

### 三件套之二:`decisions.md` —— append-only 决策日志

每个方向性判断记成一条 `DEC-NNN`。纪律:

- **只增不改。** 要推翻旧决策,不准编辑旧条目,只能新写一条,把旧的 Status 标成 `superseded by DEC-MMM`,内容保留。
- 判定要不要记的标准很土:**「六个月后的我读到这段代码,会不会想不起来当初为啥这么选?」会,就记。**

为什么 append-only?因为这是项目的**记忆**。换了会话也不会失忆 —— 新起的 agent 会话读最近几条 DEC 就能接上 scope 边界,不会推翻已经拍过板的事。可编辑的决策日志等于没有记忆:AI 会悄悄改掉历史,把自己的漂移合理化。

### 三件套之三:§8 process —— 流程金条款

专治各种「差不多得了」。这是一组**会随项目迭代增长**的流程纪律(每个 Sprint 复盘时新增),骨架条款见 [`../templates/handoff-protocol.md`](../templates/handoff-protocol.md) §8。代表性条款:

- **验收 SOP** —— Director 收到「done」后必须走固定步数核对,漏一步算违例。
- **Director 自缚条款** —— 顺手能改的只有「换字面量 / 改单条件」;超过 3 行、跨文件、或动了类型,**必须派任务**。
- **idle 上限** —— agent 卡住多久必须上报,不许干等。
- **Coordination 字段** —— 派工单必须显式列出跨角色风险。
- **hook 批处理** —— 多个小改集中过 hook,减少噪声。
- **agent housekeeping** —— 每个角色维护自己的 tasks.md,不留悬置 task。
- **Sprint 边界** —— 一个 Sprint 末要有「用户可见物」。
- **DD-first** —— 设计文档先行,再派实现。
- **detection-gate / inline 准入** —— 见 §4。
- **类型变更 codify DEC** —— 改了接口 / 数据结构必须落一条 DEC。
- **四命令验证 + 领域正确性 audit gate** —— 见 §4。

§8 的精髓:**流程本身会自我迭代。** 每次翻车或低效,复盘时把教训固化成一条新金条款,下次就不会再踩。kit 给的是骨架,你的项目会长出自己的条款。

## 4 / 机器 gate 理念:结论先过门,再信

光有人和流程不够。**AI 张口就来「我测过了」,十句有三句不能信。** 所以设几道机器闸 —— 让机器替人守门,任何结论先过门再信。

### 四命令验证(代码任务)

任何代码任务交接前必须跑全套验证命令,**并把数字贴出来**。典型四条(按项目技术栈替换):

```
test    单元/集成测试全绿
tsc     类型检查无错(或对应语言的编译/类型门)
e2e     端到端冒烟
build   产物能构建出来
```

「看起来对」不算数;「测试绿了 + 数字贴出来」才算。

### 视觉 detection-gate(玩家可见层)

任何动 UI / 视觉 / 用户可见文字的活,**Director 必须亲自把东西开起来用眼睛看过**才签字,不能只信「测试绿了」。原因:UI 层往往零测试覆盖,且视觉问题(穿模、残留、错位)测试根本测不到。

进阶:把「能自动检测的视觉回归」做成 detection-gate(截图比对 / DOM 断言),把「只能人眼判断的」留给 Director 实测。**inline 准入** = 只有当一个视觉效果能被机器检测时,才允许 inline 进主流程;否则先单独验证。

### 领域专属正确性 audit gate

这是最值钱的一道,**也是 kit 里最需要你为 `<PROJECT>` 定制的一道**。它的通用模式是:

> **找到你项目里那个「靠人眼根本审不出、但一旦错了就致命」的正确性维度,写一个工具去穷举/校验它,做成一行命令的 gate,任何相关改动必须过这道闸并贴出结果。**

举例(来自源项目):一款关卡制游戏,「每一关到底能不能通关」靠人肉试玩根本审不全。于是写了个求解器穷举,做成 `npm run audit:levels`,任何改关卡数据的任务必须贴出「N/N 可过、0 死关」才算完,并把这条规则固化成一条 DEC。

换到别的领域,这道 gate 可能是:数据管线的 schema/不变量校验、API 的契约测试、ML 模型的回归基线、账目的对账脚本 …… 模式一样:**可机器穷举的正确性 + 一行命令 + 强制贴结果 + 落 DEC。**

### 一个真实教训:工具本身也要先过门

源项目有一次:为了排查「哪些关无解」,临时写了个粗糙求解器,跑完报告「8 关无解」。Director 信了,还得意地写进状态板。结果人肉一试,假的 —— 那破求解器搜索深度太浅,搜不到解就当「无解」,8 个全是假阴性。

教训:**AI 给的结论,哪怕它说得再像那么回事、哪怕你已经信了,也得先问一句「你这工具校准过没有」。** 后来把求解器做成正式工具,并加了一道**自我验证门** —— 它得先证明能解开那些「已知能过」的样本,通过了才信它的判断。

这就是机器 gate 理念的闭环:**不仅用机器门验结论,连机器门本身也要先被验证。**

## 5 / 进化史:从「手动启动咒」到 `claude --agent` + hook

这套机制最得意的进化,是**派工方式本身**。

### 第一代:手动启动咒(靠自觉,会漏)

早期派活,Director 吐出一长段「启动咒」—— 几十行 prompt 模板,用户复制粘贴到新会话里,会话再「自觉地」去读全局约束、读角色、读看板。

问题太明显:每次粘贴都可能漏读、跑偏,「启动前必读那三步」全靠 AI 自觉。AI 的自觉……你懂的。

### 第二代:`.claude/agents/<role>.md` + SessionStart hook(强塞,漏不了)

把 9 个角色固化成 `.claude/agents/<role>.md` 文件(frontmatter 定义角色 + body 写协议),配一个**开机自动注入的 SessionStart hook**(`inject-role.sh`),会话一启动就把全局约束、角色定位、看板、最近决策**强行塞进上下文**。

裸启动 = Director(由 `.claude/settings.json` 的 `{"agent":"director"}` 决定)。派活从此一行命令:

```bash
claude --agent <role> "<task-id>: 一句话任务 · handoff 在 team/<role>/notes/<id>-*.md"
```

```
旧:Director 吐出整段「启动咒」(40+ 行 prompt)
     → 用户复制粘贴 → 会话自觉去读约束(靠自觉,会漏)

新:claude --agent <role> "<task-id>: 一句话 · handoff 路径"
     → 开机 hook 自动注入约束/角色/看板/决策(塞进去,漏不了)
```

**这一步的本质:把「靠 AI 自觉」换成「机器强塞」。** 它让整条流水线从「能跑」变成「跑得稳」。旧启动咒不删,降级为 fallback(hook 未生效 / 临时手动起 session 时用)。

> kit 里 [`../templates/.claude/`](../templates/.claude/) 直接给了这套:`settings.json` + `agents/<role>.md` × 9 + `hooks/inject-role.sh`。拷过去填占位符即可。

## 6 / 经验教训

把踩过的坑摊开,比吹方法论有用。

1. **AI 工具的结论默认不可信,先过验证门。** 「我测过了」「这关无解」「8 个 bug 全修了」—— 一律先要数字、先要可复现的机器证据。连你自己写的校验工具,也要先证明它能识别已知正确样本。这是整套打法的地基。

2. **Director 防漂移是真值钱。** 上面那个求解器乌龙,一个 Director 都已经信了、还写进状态板的假结论,正因为有验收 SOP、有「先校准工具再信它」的纪律,最后被纠了回来,没变成代码。防漂移机制的价值,平时看不见,翻车时救命。

3. **协调开销真实存在,别假装它不在。** 全程运营文档量可能是代码量的两倍多 —— 决策日志、状态板、派工单、复盘占大头。**你省的是「亲手敲代码」,不省「管理」。** Director 和你的人力一点没省,只是挪了位置。算账时把这块算进去。

4. **什么活适合 / 不适合**(同 README 边界,这里讲背后逻辑):
   - **适合**:边界清楚、验收可机器检查、多领域能并行、你愿意把需求讲清。因为这套打法的杠杆点是「并行 + 可验证」,这两个条件不满足,杠杆就撬不动。
   - **不适合**:模糊审美直觉(验收标准写不出 → 机器 gate 失效 → 退化成人肉试玩)、连「做什么」都没想明白(派工单都写不出 → 先去 brainstorm)、一个人 10 分钟的小事(启动整套流水线的固定成本远超收益)。

5. **真机才抓得到的坑,机器 gate 也补不全。** 例如部署到子路径后资产 404(构建工具不重写代码里的字符串字面量),只有真机一跑才暴露。所以「Director 必须亲眼看过才签字」这条人肉门,和机器门是互补的,不是冗余的。

## 7 / 一图收尾

```
Director 写派工单(Goal / Acceptance Criteria / Coordination / Not in Scope)
    │
    ▼  claude --agent <role> "<task-id>: 一句话 · handoff 路径"
    │
    ▼  SessionStart hook 自动注入(HARNESS + persona + tasks + 最近 DEC)
    │
 Agent 执行 ──► 每个 milestone append 执行日志
    │
    ▼  机器 gate:四命令验证(test/tsc/e2e/build)+ 领域正确性 audit + 视觉人肉门
    │
 Agent 回填 Handback,status → done,更新 tasks.md
    │
    ▼  Director 验收 SOP(漏一步算违例)
    │
    ▼  方向性判断 → append 一条 DEC-NNN(只增不改)
    │
    ▼  通过 → 派下一个 task(循环);翻车 → 复盘固化成 §8 新金条款
```

要复用这套打法,记住三层:**角色拆分**(干净上下文)→ **派工闭环**(Director 调度,文档交接)→ **防漂移三件套 + 机器 gate**(摁住 AI、替人守门)。kit 的 [`../templates/`](../templates/) 把这三层都做成了带占位符的脚手架,[`../skill/SKILL.md`](../skill/SKILL.md) 帮你 bootstrap 到具体项目。
